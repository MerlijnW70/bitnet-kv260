WHAT WAS CHANGED SINCE kria-model-results.txt, AND WHAT EACH PART COST
  Three changes, in the order they were made; each has its own results file with the measurements that
  justified it, and this file re-measures the three of them together, end to end, on the board as it
  stands tonight.
  1. THE TWO-STAGE HEAD ON THE FABRIC (kria-head-results.txt; board/bitnet_kria.c, --head fabric).
     The int8 output head was 328335360 bytes read by four A53s at 6.3 GB/s, 52.1 ms of every generated
     token, 41.7% of it.  It is now: stage 1, a ternary copy of the head (head_t.bin, 82083840 B, one
     row-scale a row, rule absmean:0.6) streamed through the same four matvec engines the model already
     uses; stage 2, the top 256 rows by that approximate score recomputed EXACTLY from head_i8.bin on the
     A53s and the argmax taken over those.  Exact only if the true argmax is in the top 256, which is not
     assumed: the study measured worst rank 56 over 2115 real head states (kria-head-results.txt), and
     every id below is the check that it holds.  7.161 ms a call now, 52.309 before.
  2. THE A53 SIDE (kria-overlap-results.txt; board/bitnet_kria.c).  The K cache tiled and transposed and
     the scores NEON, four query heads riding one loaded tile row; the norms, the quantisers, RoPE, the
     residuals and the embedding decode NEON; the engine sums read where the DMA left them instead of
     memcpy'd; a pass dropped from the shift scan by an identity; the thread pool spinning before it
     sleeps; a redundant copy of the hidden state gone.  Attention 10.19 -> 7.48 ms a forward on the
     battery, the norms and their neighbours 7.27 -> 3.91, the sums out 2.25 -> 1.07.
  3. THE FABRIC'S WRITE PATH (kria-ddr-results.txt; board/build-ffn.tcl only, no RTL change).  The five
     AXI DMAs' S2MM burst 16 -> 256 beats and their S2MM memory port 32 -> 128 bits, so the int32 sums
     leave in writes of up to 4096 bytes instead of 64 and the DDR turns the bus around far less often
     between the weight reads and the sum writes.  The weight stream 12.08 -> 13.24 GB/s, the four engine
     phases 43.12 -> 39.35 ms a forward.
  Nothing else changed: the same model.bin, the same head_i8.bin and head_scale.bin, the same norms and
  embeddings, the same tokenizer, the same greedy decode, the same float32 KV cache, the same engines and
  glue RTL, the same stream format and control registers.

WHAT IS LEFT, AND WHAT THE NEXT CEILING IS
  Of a 72.05 ms generated token: the engines 39.35 (54.6%), attention 7.48 (7.5 at the battery's average
  context, 14.2 at 309 positions, 16.2 at 360), the head 7.16, the glue 6.87, the norms 3.91, the shift
  scan 2.93, the sums 1.08, the activation loads 1.09.
  1. THE ENGINES, 39.35 ms, more than half the token, at 13.24 GB/s of a DDR that was measured to hand
     out about 14.0 GB/s to all masters together.  Reads cannot go much further: the burst and the port
     arrangement were both tried and neither helped (kria-ddr-results.txt).  The only real lever left is
     FEWER BYTES: five trits a byte in base 3 (1.6 bits a weight instead of 2) would take a token's
     521.0 MB to 417.6 MB.  PROJECTION at the measured 13.33 GB/s: engines 39.6 -> 31.7 ms, head stage 1
     5.98 -> 4.8, a generated token 72.0 -> 63.0 ms, generation 13.9 -> 15.9 tok/s.  It is exact by
     construction (the same weights, the same integer sums) but it costs a 256-entry decode table a byte
     in the engine, 80 lanes, a repacked model.bin and head_t.bin, a runtime that knows the new beat
     counts, a bitstream rebuild and a full revalidation.  NOT BUILT; a projection only.
  2. ATTENTION at long context: the value accumulate, 3.26 cycles a MAC, is now the larger half and three
     forms of it were measured and rejected (kria-overlap-results.txt).  Going further means fewer bytes
     in the KV cache, and bf16 changes 19 of 31 prompts' ids - so it is a different model, not a speed
     win.  float32 stays.
  3. THE GLUE, 6.87 ms a token for two passes over 6912 elements = 123 fabric clocks an element.  That is
     the grown mul16's serial multiplier; making it a few clocks wide is a fabric change with the whole
     revalidation behind it.
  4. THE SHIFT SCAN, 2.93 ms, four sequential passes over 6912 words on one thread; splitting it over the
     pool is possible now that a dispatch is a spin, and was not tried.
  5. THE TWO HALVES CANNOT BE FILLED FURTHER WITHIN A TOKEN.  The side thread carries 4.68 ms a forward
     off the critical path and the main thread waits 0.100 ms on it.  Every remaining arrow in the chain
     is a true dependency, and the stage-2 rescore in particular cannot overlap the next forward because
     it is what names the next token.  Filling both halves needs two tokens in flight - speculative
     decoding or a batch - and that is a different model or a second sequence, not a speed change to this
     runtime.

HOW TO REPRODUCE, on the board
  gcc -O3 -Wall -Wextra -std=c11 -march=armv8-a+crc -ffp-contract=off -o bitnet_kria bitnet_kria.c -lm -lpthread
  python3 provebench.py --exe baseline/bitnet_kria --no-head-flag --repeats 3 --out prove-baseline.json
  python3 provebench.py --exe ./bitnet_kria --head fabric --repeats 3 --out prove-after.json
  python3 provebench.py --compare prove-baseline.json prove-after.json
  python3 headcheck.py ids-prove-fabric.json --head fabric --exe ./bitnet_kria
  python3 headcheck.py --compare baseline/ids-arm-baseline.json ids-prove-fabric.json
  python3 headcheck.py ids-prove-arm.json --head arm --exe ./bitnet_kria
  python3 breakdown.py baseline/ids-arm-baseline.json ids-prove-arm.json ids-prove-fabric.json
  python3 flagcheck.py ids-prove-fabric.json bench:crc32 --exe ./bitnet_kria -- --threads 1
  sudo ./bitnet_kria --stage-check refdump/stages.bin --head fabric --timing
  sudo env EXE=./bitnet_kria FLAGS='--head fabric' NEW=256 CTX=512 ./power-bitnet.sh
