BitNet b1.58 2B4T on the Kria KV260: FIVE TRITS A BYTE, FOUR POSITIONS A PASS, AND THE SAME WORDS.
The weight stream carried four ternary weights a byte, two bits each, of which only three of the four
codes were ever used.  It now carries five a byte in base 3 - byte = sum of (w_j + 1) * 3^j for j = 0..4,
so 243 of the 256 codes are used - and the bytes a generated token streams fell 603,095,040 -> 483,213,312.
The engines learned at the same time to hold four activation vectors and answer one pass of the weight
stream for all four, so the prompt runs four positions at a time.  Before either of those the ARM work was
moved under the streams that were already running.  This file is the PROVE pass: everything below was
measured on 2026-09-07 between 05:42 and 06:16 UTC in ONE session on a quiet board, the before and the
after taken back to back with a bitstream swap between them, and every id compared in place.

  Of a 59.6 ms generated token at the bench prompts' context:
    the engines' weight stream   32.80 ms   55.0%
    the two glue passes           6.85      11.5%
    the head                      5.43       9.1%   (4.12 of it its own ternary stream)
    attention                     4.78       8.0%   (14.6 ms at 360 positions)
    norms, quantisation, RoPE     3.50       5.9%
    the shift scan                2.50       4.2%
    the activation loads          0.88       1.5%
    the sums out of the buffer    0.28       0.5%
  The fabric holds 77% of the token; 61.9% of it is weight bytes moving.

  THE PACKING IS FINISHED.  These weights carry about 1.55 bits of entropy each and base 3 spends 1.585
  (8 bits / 5 weights).  Under 2% is left between this packing and the entropy floor, and taking it would
  need a variable-length code the fabric would have to decode serially.  There is no next fifth.

  WHAT IS THERE, in the order I would take it:
  1. FEWER, LONGER ENGINE RUNS - the biggest measured gap, 6.70 ms a token.  The model stream takes
     32.80 ms against the fabric's 26.10 ms floor.  That gap is NOT the memory: the head stream, one long
     sequential read of 65,667,072 bytes, runs at 15.93 to 16.01 GB/s - the four engines' whole beat rate -
     and it runs at that rate on the same DDR in the same token.  What differs is that the model is streamed
     in 120 short runs a token (four engine phases over thirty layers), each with its activation reload,
     its register writes, its DMA descriptor setup, its completion poll and its drain.  The two-bit
     stream carried the same 6.9 ms of it; base 3 did not create this, it only made it a larger share.
  2. BATCHED GENERATION ACROSS INDEPENDENT CONVERSATIONS.  The engines already answer one pass of the
     stream for four vectors and the prompt already uses it; generation cannot within one conversation,
     because token t + 1 needs token t, but four separate conversations have no such dependency and
     ctrl[10:9] already carries the batch.  PROJECTION, not measured: at two passes a batch of four, the
     stream would cost about 16.4 ms a token each against 32.80.  Nothing in the fabric would change; the
     token loop would.
  3. THE GLUE, 6.85 ms a token in two passes over 6912 elements - 11.5% of a token, and the one part of
     the pipeline that has not been looked at since it was built.
  PROJECTIONS, each marked as one and none of them measured: lever 1 taken in full would put a token at
  59.6 - 6.7 = 52.9 ms, 18.9 tok/s.  Lever 2 taken in full would put it at 59.6 - 16.4 = 43.2 ms for each
  of four conversations, 23.1 tok/s each.  They do not simply add - lever 2 halves the very stream lever 1
  shortens - and the floor under both, every ARM millisecond hidden and every byte moving at the beat
  rate, is the 30.2 ms the fabric needs, 33 tokens a second.

THE OPEN ITEM, HONESTLY: THE SHIFT-SCAN STALL
  Sometimes a run's shift scan costs three to eight times its 2.7 ms norm and the whole forward wears it.
  Tonight it hit three of the 31 prompts of the batch-4 battery (q20_forloop 20.257 ms a forward,
  q22_nl_uitleg 7.993, q11_wordproblem 7.850) and none of the 31 of the batch-1 battery, none of the six
  360-position runs, and none of the three bench repeats.  It is not the batch's and not base 3's: the
  same stall appears in the two-bit runs of last night and in --prompt-batch 1 runs.  It is worth 2.4 ms
  a token on a battery average when it lands and nothing when it does not.  It is not diagnosed and it is
  not a regression, but it is the reason a battery figure and a bench figure disagree by more than noise,
  and it should be chased before the next round of numbers is taken.

  A SECOND TRAP, FOUND TONIGHT: after the model files are swapped, the first run reads the model from
  storage instead of the page cache - 8.13 s at 51 MB/s against 0.87 s at 482 MB/s - and its first prompt
  is worthless (6.52 tok/s prompt, a 967 ms shift scan on one forward) while the readahead is still in
  flight.  The very same process's second and third repeats gave 29.11 / 16.81 tok/s.  Discard the first
  repeat after any swap; do not average it in.
  AND THE OLD TRAP STILL STANDS: measure on a quiet board.  An ssh login while a run is in flight takes a
  core off four spinning pool threads.  Every number above was taken with nothing logged in and nothing
  polling: both measurement scripts were launched detached and waited for by a single connection that
  slept on the board until a marker file appeared.
